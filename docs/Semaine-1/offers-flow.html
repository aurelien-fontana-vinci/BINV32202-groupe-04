Du navigateur aux données

Comment une offre arrive à l’écran

Le parcours de la liste des offres traverse l’interface React, l’API Express et SQLite. Les droits et la visibilité sont décidés côté serveur; le navigateur ne reçoit que le DTO destiné à l’affichage.

Requête frontend · proxy Vite vers le backend GET /api/offers Route Express · authentification requise GET /offers

Architecture du projet

Un monorepo npm à deux applications, reliées par un contrat JSON documenté.

01 · Interface

React + TypeScript + Vite

Les pages assemblent hooks et composants; les services appellent l’API, les modèles décrivent ses données.

02 · Serveur

Express en couches

Les contrôleurs gèrent HTTP, les services les règles métier, les repositories le SQL et les mappers les conversions.

03 · Persistance

SQLite + migrations SQL

Les contraintes relationnelles vivent en base. Les évolutions du schéma passent par de nouvelles migrations numérotées.

04 · Vérification

Tests isolés par couche

Vitest et Supertest côté backend sur SQLite en mémoire; Vitest et Testing Library côté frontend avec fetch simulé.

Référence : architecture détaillée · commandes et installation : README.

Le parcours des offres

La réponse remonte ensuite vers la page, qui distingue chargement, erreur, liste vide et tableau de résultats.

  1. 01

    La route frontend est protégée

    App appelle useAuth une seule fois. Un utilisateur autorisé à lister les offres accède à /offres; la page reçoit utilisateur, jeton et callback de déconnexion.

    frontend/src/App.tsx
    frontend/src/utils/permissions.ts
  2. 02

    La page déclenche le chargement

    OffersPage appelle useOffers(token, onUnauthorized), puis rend les états de chargement, d’erreur, vide ou le tableau.

    frontend/src/pages/OffersPage.tsx
  3. 03

    Le hook orchestre la requête

    useOffers crée un AbortController, met à jour les offres à la réponse et annule la requête si le composant est démonté. Un 401 déclenche la déconnexion.

    frontend/src/hooks/useOffers.ts
  4. 04

    Le service envoie le jeton

    getOffers appelle /api/offers avec l’en-tête Authorization. Il vérifie le statut et valide le JSON avec isOfferList.

    frontend/src/services/offers.service.ts
    frontend/src/utils/guards.ts
  5. 05

    Express authentifie puis autorise

    app.ts place authenticate avant le routeur. La route vérifie ensuite canListOffers; les contacts sans rôle déposant reçoivent 403, une session invalide 401.

    backend/src/app.ts
    backend/src/controllers/offers.controller.ts
    backend/src/services/permissions.ts
  6. 06

    Le service fixe la visibilité

    Administrateur : toutes les offres. Étudiant : offres publiées. Déposant : ses offres, quel que soit leur statut. Ce filtre protège les résultats indépendamment de l’interface.

    backend/src/services/offers.service.ts
  7. 07

    Le repository lit SQLite

    La requête joint offers à companies, academic_years et periods; elle applique les filtres de visibilité puis trie par année et création, décroissantes.

    backend/src/repositories/offers.repository.ts
    backend/src/db/migrations/001_initial.sql
  8. 08

    Les mappers préparent le DTO

    La ligne SQL devient un modèle métier, puis un DTO réduit à id, title, companyShortName, academicYear, period et status.

    backend/src/mappers/offer.mapper.ts
    backend/src/models/offer.ts
  9. 09

    React affiche le résultat

    Le tableau affiche titre, entreprise, année, période et statut. Les codes de période et de statut sont traduits en libellés français.

    frontend/src/components/OfferTable.tsx
    frontend/src/utils/labels.ts

Ajouter un filtre par période

Le filtre doit réduire les résultats sans remplacer les règles de visibilité existantes.

FichierResponsabilité du changement
frontend/src/pages/OffersPage.tsxAjouter le contrôle de période et conserver sa sélection; afficher toutes les périodes par défaut.
frontend/src/hooks/useOffers.tsTransmettre le filtre au service et relancer proprement le chargement lorsque sa valeur change.
frontend/src/services/offers.service.tsSérialiser la valeur sélectionnée en paramètre facultatif, par exemple ?period=P1.
backend/src/controllers/offers.controller.tsLire et valider le paramètre HTTP; rejeter une valeur inconnue ou répétée avec une erreur cohérente.
backend/src/services/offers.service.tsCombiner le filtre de période avec le filtre de rôle; ne jamais laisser le paramètre contourner la visibilité.
backend/src/repositories/offers.repository.tsÉtendre OfferFilter et ajouter la condition SQL sur periods.code, en gardant les filtres actuels.
backend/API.mdDocumenter le paramètre, les valeurs acceptées (P1, P2, OTHER) et les erreurs possibles.
backend/tests/offers.test.tsTester le filtre pour les profils, les périodes sans résultat et les paramètres invalides; vérifier que les droits restent appliqués.
frontend/tests/OffersPage.test.tsxTester le contrôle, le paramètre envoyé et les résultats affichés après sélection.

Contrat conseillé

Un paramètre facultatif period accepte P1, P2 ou OTHER. Sans paramètre, le comportement actuel reste inchangé.

À préserver

L’administrateur garde toutes ses offres dans la période choisie; l’étudiant ne voit que les offres publiées; le déposant ne voit que les siennes.

Pas de migration prévue : l’offre contient déjà period_id, la période est reliée à son année académique et la requête joint déjà la table periods. La valeur de période est également présente dans les modèles et le DTO actuels.

Garde-fous existants

Les tests proches du parcours servent de point de départ pour vérifier une évolution.

API

offers.test.ts couvre authentification, accès par profil, visibilité et forme du DTO sur une base SQLite en mémoire.

Interface
