Audit des tests des candidatures — EF-32 et EF-33

Audit ciblé des tests API et interface pour la candidature à une offre publiée, le retrait, les droits et la consultation des statuts. Aucun code applicatif n’a été modifié.

Aucun manque P0 identifié. Les contrôles API couvrent les refus importants. Les lacunes restantes sont ciblées : confirmer qu’un retrait croisé ne modifie pas la candidature d’origine, exercer les erreurs de soumission dans l’interface et couvrir l’offre dont la candidature est déjà retirée.

Cas à vérifier Test existant et assertion utile Manque confirmé ou constat écarté
Refus d’une candidature à une offre non publiée applications.test.ts : la réponse vérifie 409 et le code OFFER_NOT_PUBLISHED. Écarté : refus API directement couvert.
Retrait d’une candidature déjà traitée applications.test.ts : test paramétré sur les candidatures retenue et non retenue ; les deux vérifient 409 et APPLICATION_ALREADY_PROCESSED. Écarté : les deux statuts traités sont couverts.
Liste personnelle : ne pas exposer les candidatures d’un autre étudiant applications.test.ts : le test vérifie 200, les candidatures attendues, puis compare exactement les identifiants retournés aux identifiants d’Inès. Écarté : l’assertion exacte détecte toute candidature tierce ajoutée à cette liste.
Un étudiant tente de retirer la candidature d’un autre applications.test.ts : Inès tente de retirer la candidature de Lucas ; la réponse doit être 404 avec APPLICATION_NOT_FOUND. Manque confirmé, limité à la non-modification : le test vérifie le refus, mais ne relit pas la candidature de Lucas pour confirmer qu’elle reste IN_PROGRESS. Ajouter cette assertion après la tentative.
Accès direct à la page candidatures avec un profil non étudiant App.test.tsx : la session administrateur ouverte directement sur /candidatures donne « Page introuvable » et aucune requête /api/applications. Écarté : le manque antérieurement repéré est désormais couvert par ce test de route.
Échec de la soumission d’une candidature dans l’interface OffersPage.test.tsx vérifie seulement le parcours réussi, le POST et l’affichage « En cours ». L’API vérifie le doublon 409 APPLICATION_EXISTS dans applications.test.ts. Manque confirmé : aucun test UI n’exerce l’erreur d’action. Simuler le POST en 409, vérifier l’erreur affichée et l’absence d’un statut de candidature ajouté à tort.
Afficher une offre déjà liée à une candidature retirée ApplicationsPage.test.tsx couvre le libellé « Retirée » sur la page des candidatures ; le test d’offre OffersPage.test.tsx ne teste que la création d’une candidature. Manque confirmé pour cette vue : fournir une candidature WITHDRAWN au chargement, puis vérifier le statut retiré et l’absence du formulaire « Candidater ».

Plan de test recommandé

  1. Après le retrait croisé refusé, relire la liste de Lucas et vérifier que sa candidature est toujours IN_PROGRESS.
  2. Dans OffersPage.test.tsx, couvrir le POST en erreur 409 et vérifier le rendu de l’erreur sans mise à jour optimiste.
  3. Couvrir dans la même page le cas d’une candidature préexistante WITHDRAWN : statut affiché, aucun formulaire de candidature.
