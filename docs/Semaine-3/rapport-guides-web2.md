# Audit des guides du dépôt au regard de Web 2

**Date :** 10 novembre 2026
**Objet :** comparer les consignes applicables à l’agent et les guides du projet aux attentes Web 2 effectivement retrouvées dans les supports fournis. Il s’agit d’un audit ; aucun guide du projet n’a été modifié.

## Périmètre et méthode

Les consignes agent dédiées repérées sont le fichier [`AGENTS.md`](../../AGENTS.md). Je n’ai trouvé ni `copilot-instructions.md`, ni instructions Copilot sous `.github`, ni autre fichier `AGENTS.md`. J’ai lu en entier les guides du dépôt cités par ces instructions : [`README.md`](../../README.md), [`docs/architecture.md`](../architecture.md), [`backend/API.md`](../../backend/API.md), [`docs/seed.md`](../seed.md), ainsi que le modèle de pull request [`.github/pull_request_template.md`](../../.github/pull_request_template.md) et [`backend/.env.example`](../../backend/.env.example). J’ai également consulté [`.vscode/settings.json`](../../.vscode/settings.json) : il définit les permissions, l’approbation des commandes et la sandbox de l’agent, pas des conventions de programmation web ; il n’est donc pas comparé dans le tableau. Le cahier des charges décrit des exigences produit ; il ne constitue pas un guide de développement.

Les sources de cours ci-dessous sont les PDF présents dans `docs/Semaine-3/th_web2/1. Présentation du cours/`. Les numéros indiqués sont ceux des diapositives tels qu’imprimés dans les supports. Je n’ai pas retenu une attente faute de source : aucun des supports fournis ne mentionne explicitement l’accessibilité, ARIA ou les tests automatisés.

## Bilan et recommandations

Les guides couvrent bien les frontières client/serveur, les routes et réponses REST, les responsabilités des couches, les composants React et la séparation des accès. Ils sont adaptés au projet et ne contredisent aucune consigne Web 2 vérifiée.

Les améliorations de guide les plus utiles seraient :

1. préciser l’ordre des middlewares Express et l’emplacement du gestionnaire d’erreurs ;
2. formuler la convention d’annotations TypeScript si elle est bien exigée pour ce projet ;
3. ajouter les consignes de formulaires contrôlés et de traitement des erreurs réseau/effets asynchrones ;
4. compléter le rappel JWT par la non-confidentialité du payload et la sensibilité du jeton.

L’accessibilité n’est pas évaluée dans cette comparaison : aucun support Web 2 fourni ne contient une consigne vérifiable à ce sujet. De même, les tests et `npm run check` figurent bien dans les guides du dépôt, mais les supports Web 2 consultés ne les énoncent pas comme attentes ; je les traite donc comme des conventions projet, pas comme des exigences attribuées au cours.

# Optionnel
## Proposition de senseur d’architecture

### Règle et intérêt

Le backend répète un découpage par couches pour ses fonctionnalités : contrôleur, service, repository et mapper. Une règle de frontière déjà écrite dans [`AGENTS.md`](../../AGENTS.md) et [`docs/architecture.md`](../architecture.md) dit que les services ne dépendent pas des objets Express `Request` et `Response` ; les contrôleurs gardent la validation et les réponses HTTP, tandis que les services portent les règles métier. Le graphe d’architecture de [`docs/architecture.md`](../architecture.md) montre ce patron pour entreprises, offres et candidatures.

Le risque récurrent n’est pas une violation actuellement observée, mais une régression possible à chaque nouvelle route : mettre un accès à `req`/`res` ou à leurs types dans un service pour gagner du temps. Cela couplerait la logique métier au transport HTTP et rendrait les services moins simples à réutiliser/tester.

### Senseur proposé

- **Moment :** test d’architecture automatisé exécuté par Vitest dans `backend/tests/`, inclus dans `npm run test` et donc dans `npm run check` avant intégration.
- **Données examinées :** les fichiers TypeScript sous `backend/src/services/`, analysés avec l’API AST de TypeScript déjà présente dans le projet. Le contrôle vérifie les imports nommés provenant de `express` : les symboles importés `Request` ou `Response` (y compris les alias) sont interdits dans cette couche.
- **Résultat produit :** succès si aucun import interdit n’est trouvé ; sinon échec du test avec chemin de fichier, ligne et symbole importé. Le message indique de déplacer la lecture/validation HTTP dans le contrôleur et de transmettre au service des valeurs métier simples.
- **Exemple de violation :** `import type { Request } from "express";` dans `backend/src/services/applications.service.ts` ferait échouer le contrôle avant que la modification soit intégrée.
- **Pourquoi ce choix :** cette règle est explicite et bornée ; elle protège une séparation déjà adoptée sans installer une nouvelle dépendance ni analyser toute l’architecture.

### Faux positifs, limites et coûts

- Un import de `Request`/`Response` pourrait être inutilisé ou accidentel : il échouerait tout de même. C’est souhaitable dans ce dossier, mais le diagnostic doit rester précis.
- Ce contrôle ciblé ne détecte pas nécessairement un type HTTP renommé/re-exporté depuis un module local, un accès indirect à `req` transmis sous un autre nom, ni une dépendance sémantique équivalente. Il détecte l’import direct depuis `express`, pas toutes les formes de couplage.
- L’analyse AST demande un petit test à maintenir si l’organisation des services change. Le coût d’exécution devrait être faible, mais il n’a pas été mesuré puisque le senseur n’est pas implémenté.
- Il ne remplace ni la revue de code ni les tests de comportement ; il ne valide pas non plus les autres frontières (par exemple SQL limité aux repositories).

## Restitution courte

> Les guides de Gesta couvrent bien les principales conventions vues en Web 2 : séparation client/serveur, REST, responsabilités des couches et composants React. Ils sont moins explicites sur les formulaires contrôlés, les échecs réseau et certains détails de sécurité des JWT. Les supports fournis ne permettent pas d’affirmer que l’accessibilité ou les tests automatisés étaient une consigne de cours, donc je ne les présente pas comme telles. Pour prévenir les dérives d’architecture, je propose un test Vitest qui inspecte les services backend et échoue s’ils importent `Request` ou `Response` depuis Express. Il fournirait un retour rapide à chaque `npm run check`, avec un coût faible, tout en restant limité aux imports directs.
