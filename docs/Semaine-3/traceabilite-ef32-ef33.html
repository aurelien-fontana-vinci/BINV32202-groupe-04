Les candidatures à l’épreuve des tests

Cette matrice relie les exigences EF-32 et EF-33 travaillées à la Semaine 2 aux cas de test réellement présents. Un test vert atteste seulement le scénario qu’il exécute, pas l’ensemble de l’exigence.

Source des exigences
Plan de séance : docs/Semaine-2/plan.md.
Le retrait définitif est une décision métier confirmée pendant la séance.

Lecture : « Couvert » signifie qu’un test vérifie directement le comportement indiqué. « Partiel » indique une vérification d’une partie du parcours, d’un seul état ou d’une seule couche. « Lacune » signifie qu’aucun test correspondant n’a été trouvé. Les tests front utilisent fetch simulé : ils ne constituent pas une validation dans un navigateur réel.

Tests présents, mais pas des preuves directes de EF-32/EF-33

  • db/seed.test.ts vérifie la cohérence des données de démonstration (statuts présents, candidature retenue correspondant au stage). Cela protège le seed ; cela ne vérifie pas à lui seul l’API de consultation ou de candidature.
  • db/migrations.test.ts vérifie l’application des migrations sur une base vierge, leur non-répétition et les clés étrangères. C’est une vérification d’infrastructure, pas une preuve fonctionnelle complète.
  • Les autres cas de OffersPage.test.tsx concernant le filtre de période et les libellés des offres ne sont pas rattachés aux exigences de candidatures.

Ce que la matrice révèle

  • Les cas prioritaires manquants ont été ajoutés aux tests API : état REJECTED au retrait, accès du retrait (session et rôle), retour des quatre statuts dans les listes personnelles, et message de 4 096 caractères.
  • Une limite subsiste : le test du lien de navigation n’essaie pas d’ouvrir directement la route avec un autre profil. Le contrôle API des accès est testé séparément ; aucune vérification manuelle navigateur n’a été faite.
  • Les tests frontend simulent les réponses avec fetch ; ils ne prouvent pas le comportement dans un vrai navigateur. Les tests backend utilisent SQLite en mémoire.
  • La réussite de npm run check confirme les contrôles exécutés, mais n’élargit pas les assertions à des scénarios qui ne figurent pas dans les tests.

Vérifications exécutées après les ajouts

  • npm run test -w backend -- tests/applications.test.ts — réussi : 1 fichier, 19 tests.
  • npm run check — réussi : lint et TypeScript backend/frontend ; backend 10 fichiers, 133 tests ; frontend 8 fichiers, 52 tests ; builds backend et frontend réussis.
  • Les filtres, la recherche et les 17 lignes de traçabilité ont aussi été vérifiés automatiquement ; les liens des sources existent. Aucun test destructif ou mutation de code n’a été réalisé.
Les noms de tests et leurs assertions ont été vérifiés dans les fichiers liés. L’exécution réussie d’un test n’élargit pas sa portée au-delà des assertions qu’il contient. Lien de retour : matrice des guides et senseurs.
